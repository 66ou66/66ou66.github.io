## 引子:为什么做象棋 AI

这件事的起点不太体面:我想下象棋,但赢不了游戏里的人机模式。作为软件工程在读学生,我选择了技术路线——写个程序帮我看着棋盘。最初的设想很小:截屏,认出棋子,拼成 FEN(Forsyth–Edwards Notation,用一行字符串完整描述棋盘每个格子的棋子排布和轮到谁走的记谱法,象棋引擎吃的就是它),扔给引擎,把建议打在屏幕上。等回过神来,这个"帮我看棋"的小工具已经有了眼睛(CNN 识别)、手(自动落子)、嘴(中文解说),还能一局接一局自己开新局。

git 历史从 2026-08-12 的第一次 commit 到 10-23 的最后一次,横跨 72 天,两个仓库合计 18 个 commit。如今项目 11,004 行 Python,其中 3,750 行是测试(17 个文件、211 个测试函数)。更有意思的是前史:在 git 之前,这个项目已经死过两代,全靠后来从回收站里挖出的旧版本快照才还原出原貌。便签库里甚至有一张 2026-01-02 的任务清单,写着"研究输入fen获取下一步项目""完成终极象棋外挂项目"——如果时间戳可信,这个念头比第一行代码早了七个月(便签创建时间与内容对不上,存疑,姑且记下)。

## 一、起点:两代"不太能用"的前身

这个项目经历过四代:V0(模板匹配)→ V1(CNN)→ V-1(FEN 命令行)→ V2(终极整合)。代次是复盘时起的:V-1 时间上排在 V1 之后、V2 之前,但没有"眼睛",功能上像退了一步,所以这么编号。前两代连 git 都没上,只能从回收站旧版本快照讲起。

### V0:模板匹配,10 秒看一眼

最早的版本(回收站旧版本快照,文件时间戳 2026-08-02~03)只有 64 个文件:按颜色(HSV 色彩空间,把颜色拆成色调、饱和度、亮度三个数)判红黑、15 张棋子模板图做模板匹配,每 10 秒自动截屏一次,在命令行打印棋子统计和 FEN。核心逻辑长这样:

```python
SCAN_INTERVAL = 10  # 自动截屏间隔(秒)
def do_scan(bbox, templates, debug=False):
    raw = capture_screen(bbox=bbox)
    img, region = extract_board_region(raw)
    cells = split_to_cells(img)
    for i, cell in enumerate(cells):
        if not has_piece(cell):
            continue
        co = detect_color(cell)                        # HSV 判红黑
        matched = match_template(cell, templates, co)  # 模板匹配判型
        m[r][c] = matched
    fen = board_to_fen(m)
    print(f"FEN: {fen}")
```

(来自回收站旧版本快照的 main.py,有删节)

判断有没有棋子靠的是格子中心区域的像素占比:红色占比超过 8%,或黑色占比超过 15%,就算有子(旧版本快照里的 piece_classifier.py)——粗糙,但那一晚能跑起来就是胜利。它自带的《新手必读》里还写着一句自我检讨:"当前用的是简易文字模板,识别率会低一些。"没有引擎、没有落子,本质上只是个截图翻译器——把棋盘翻译成 FEN,然后呢?没有然后了。

### V1:第一次 CNN 训练,30.7%

第二天(2026-08-03)上了真家伙:PyTorch 卷积神经网络(CNN,图像分类的标准模型),15 个分类(空格 + 红 7 类棋子 + 黑 7 类棋子),每类 2,600 张、共 39,000 张训练图,在 CPU 上训练(装的是 PyTorch 1.13.1 CPU 版,清华镜像下载约 800MB)。V1 这一代同样只存在于回收站旧版本快照里,好在当天 20:41 留下的 train_final.log 记录了结局:

> Epoch 1/30: val=20.5% → Epoch 30/30: val=30.3%,Best val accuracy: **30.7%**

30 个 epoch(把全部训练数据完整过一遍叫一个 epoch),loss 只从 1.877 降到 1.689,曲线平得让人心凉。30.7% 的逐格准确率是什么概念?比瞎蒙(约 6.7%)强,但摊到一整盘 90 格上,平均要认错 60 来格——离"能用"差着十万八千里。

为什么这么差?当时的我没留下任何分析。更遗憾的是,后面把准确率拉上去的那次训练,样本数、时长、最终指标也都没记录,现存的 xiangqi_cnn.pt(9.38MB)是某次"练好了"之后的产物,但过程失传了。这是本项目档案里第一个大窟窿:首训 30.7% 有据可查,从 30.7% 到能用的过程,没有证据。

## 三、"现在全自动对弈还不能用":差分状态机六轮进化

### v1:90 格全对才算数

8-14(abe37da)我写下了整个项目里最诚实的一句 commit 正文:"现在全自动对弈还不能用,人机对战和棋力测评有微小差异每次要重新校验"。不能用是必然的:v1 的 auto_battle.py 每次截屏识别出整盘 90 格,和上一帧做整盘指纹比对,要求逐格相等——用现行代码 docstring 的原话说,"对 CNN 识别噪声零容忍,导致等待对方永远无法稳定确认、落子回读永远 confirm_failed"。可 CNN 每次识别总有几格在抖(我后来在便签里抱怨过"偶尔有把车认成卒的情况"),一抖,"局面稳定了"这个条件就永远不成立。

### v2:只盯 2 个变化格,投票定案

转机在 2026-08-15(7147a10,"现在全自动对战能用了",+1,182 行)。核心思想写在新抽出的 board_diff.py 开头:

```
- 一步棋在棋盘上恰好表现为 2 个变化格:
    from 格:旧局面有子 → 新局面为空
    to   格:新局面有子(吃子时旧局面也有子,但被替换)
  from 与 to 的棋子必须同色。
- 其余 88 格的识别噪声完全不参与判定 —— 这是相对"全盘指纹精确匹配"的核心改进。
```

(board_diff.py:8-14)

光盯变化格还不够,单帧仍有噪声,于是配了滑动窗口投票(auto_battle.py:291-301):

```python
# 滑动窗口投票:deque(maxlen=confirm_times) 自动裁剪最旧帧。
# 真实着法每帧稳定出现 → 快速凑够票数;CNN 随机噪声格每帧
# 位置不同 → 各自最多 1 票,永远凑不够 → 既不漏检也不误检。
self._recent_candidates.append(candidates)
votes = {}
for frame in self._recent_candidates:
    for m in frame:
        votes[m] = votes.get(m, 0) + 1
if candidates:
    best = max(candidates, key=lambda m: votes[m])
    if votes[best] >= self.confirm_times:
        self.last_board = [row[:] for row in board]
```

连续 2 帧(confirm_times=2)出现同一条候选着法才算数,轮询间隔 0.8 秒;同一 commit 还加了 16 个用例的 test_board_diff.py。原理朴素得漂亮:真实着法每帧都在同一位置出现,票数蹭蹭涨;噪声格每帧换地方,各自永远只有 1 票。

效果怎么量化?说实话:没有数字。没记成功率,也没记卡死率,能引用的只有两条 commit 信息本身的对比——8-14"还不能用",8-15"能用了"。(2026-08-15, 7147a10)

### v3 → v6:四个补丁的故事

v2 上线不是终点,8 月中下旬状态机又小步迭代了四轮(v3/v4/v6 没有独立 commit,改动混在其他提交里,时间上只能按"8 月中下旬"模糊处理):

- **v3,偶发"落子回读确认失败"**:我方落子后程序回读棋盘确认,标准是"恰好 2 格变化"——可如果对方在我落子的同时也走完了,实际是 4 格变化,被误判成失败。修法:放宽为 contains_move,容忍这种叠加。
- **v4,"等待对方卡死,一直在找窗口"**:根因发现"恰好 2 变化格"这个条件本身有毒——CNN 噪声让 diff 恒大于 2,而噪声格每帧随机,永远凑不齐"恰好 2 格"。修法:用 moves_in_diff 从 diff 里枚举所有合法候选单步,再交给滑动窗口投票。
- **v5(2026-08-19, 1e43db4"解决长将问题,把一局fen喂给引擎"),两个修复**。其一,把整局着法历史喂给引擎:

```python
if moves:
    # 喂完整着法历史:引擎据此激活长将/重复将军/长捉等循环规则
    # (只发 position fen 时循环规则永不触发,导致被标记"长将")
    self._send(f'position fen {fen} moves {" ".join(moves)}')
else:
    self._send(f'position fen {fen}')
```

(engine_wrapper.py,1e43db4 引入)

  背景是:引擎只看单个 FEN 时,长将(靠连续将军强迫对方不断应将、局面循环不变,按规则判负)、重复局面这类循环规则根本不会触发,程序会被"标记长将"而收到废着。其二,修了执黑必现的 bug:start_fen 的轮次被写死成 'b',引擎按"该红方走"返回红方着法,程序就把红子当黑子去点(auto_battle.py:242-245)。
- **v6,落子确认改为"180 秒内持续点击→回读,超时才暂停"**(CONFIRM_TIMEOUT=180.0),不再固定重试几次就放弃。

中间还插了一个体验补丁(2026-08-17, b416107"优化了黑方第一步要自己手动的缺点"):以前执黑开局,程序只会干等红方先走,还得我手动点一下;改成把当前屏幕棋盘与标准开局局面做差分,发现存在红方棋子的起点格变化,就判定红方已走、直接接管——判据复用 moves_in_diff,单个噪声格构不成完整着法,不会误判。

这段时期还加了一道防呆:识别崩溃检测(advisor.py:267-281)。对手投降或超时会跳到结算界面,棋盘消失,CNN 会在一帧垃圾画面上"自信地"误判出大量超出规则上限的棋子——实测一次修正数冲到 36 格;于是定下规矩:单帧修正数 ≥15 就判定"对局已结束",免得把垃圾识别当真实局面去点鼠标。

还有个不起眼但重要的细节:确认成功后,下一轮差分的基准用"干净的预期局面"(走子前局面 + UCI 推演),而不是带噪声的回读帧——不然噪声会被写进基准,后续差分永远不稳(auto_battle.py:476-478)。

## 四、把 90 次前向压成 1 次:[1] 键识别提速

便签里(2026-09-28 拍照)的原话:"1键识别太慢了"。

为什么慢?xiangqi_cnn.py 的 docstring 写得很清楚:整盘识别要给 10×9=90 个格子分类,若逐格调用单格分类函数,就是 90 次独立的模型前向 + 90 次"内存→计算→内存"的往返,在没有 GPU 的 CPU 上极慢——"[1] 键识别慢的主因之一"。

2026-09-25(2ad8f43"加快了点1键识别速度")把 90 个小图叠成一个 batch,只做一次前向(xiangqi_cnn.py:459-477,摘录):

```python
# 直接按 (N, 3, H, W) 填 NCHW 连续内存:与训练时 DataLoader(torch.stack)
# 的排布一致,展平时也不会踩到 memory format 的坑。
batch = np.empty((len(valid), 3, CELL_SIZE, CELL_SIZE), dtype=np.float32)
for k, i in enumerate(valid):
    img = cv2.resize(patches[i], (CELL_SIZE, CELL_SIZE))
    img = cv2.cvtColor(img, cv2.COLOR_BGR2RGB).astype(np.float32) / 255.0
    batch[k] = img.transpose(2, 0, 1)          # HWC -> CHW
tensor = torch.from_numpy(batch).to(self.device)
```

为什么批量了结果还不变?模型处于 eval() 模式,BatchNorm(批归一化层,推理时用训练期固定的运行统计量)逐样本独立,批量推理与逐格推理结果一致,只有浮点误差级别。

顺路还踩了个坑:把展平操作从 view 改成 reshape——CPU/MKLDNN 在输入为 channels_last 视图时会输出 channels_last 特征图,此时 x.view 直接抛"view size is not compatible"异常:

```python
# 输入连续时 reshape 完全等价于 view(结果与内存都一致),只有不连续时才拷贝。
x = x.reshape(x.size(0), -1)
```

(xiangqi_cnn.py,2ad8f43)

数字变化:代码注释里留了三个可引用的说法——"比逐格调用 _classify_cell_full 快一个数量级"(xiangqi_cnn.py:533-535);"叠加帧数 5→3、间隔 0.12→0.05,[1] 键整段识别耗时实测约降到原先的 1/3"(同 commit 的 advisor.py 注释;那个 5 帧的旧版本没在任何 commit 里出现过,是本地未提交状态还是别处实现,已不可考);测试注释里还有一条"真模型对 90 格做一次 128×128 卷积在 CPU 上要约 1 秒"(test_cnn_batch_infer.py:53),可作优化后单次整盘前向的量级参考。优化前到底几秒?没记下具体秒数,不编。同一批提交还加了 10 个用例的 test_cnn_batch_infer.py,专门锁定"batch==90 且只有 1 次前向"和"批量与逐格结果逐格一致"——防止以后被改回去。

有意思的连锁反应:批量前向快到单帧也够用之后,靠多帧投票压噪声的需求消失了。同日 733f541 把投票帧数 3→1,注释称"识别端耗时约再降到 1/3";多帧投票从"必需品"降级成"可选件"(能力保留,需要时调回 3 即可)。

一个诚实的脚注:便签拍照是 09-28,批量优化提交是 09-25,三天后便签上居然还写着"1键识别太慢了"——可能是照片记录的是修改前的状态,也可能是没完全见效,档案无法裁决,存疑。

## 五、"引擎乱给答案":180° 的镜像

2026-09-25 晚(012d14f,commit 标题就叫"把引擎乱给答案改了")。现象是引擎开始胡乱支招,着法的列号和进退方向全不对。原因在方向检测:程序要知道玩家执红还是执黑,才能决定屏幕棋盘要不要翻转;旧判据是"红像素比例"启发式——中盘顶/底行棋子一变,比例就失真,玩家执黑(红在屏幕上方)时被误判成执红,整盘 180° 翻转。引擎盯着一个上下颠倒的棋盘,给出的可不就是"乱给答案"。

修法(fen_utils.py:131-177, infer_orientation):彻底不看像素比例,以棋盘内容为准——第一优先,开局时顶/底行整列满子判色;第二优先,找将/帅的九宫位置:帅恒在 y=7..9、将恒在 y=0..2,帅在下半场就是执红视角,反之执黑。中盘找不到依据时,沿用已锁定的方向;而且方向只在首次识别时检测一次并锁定(advisor.py:121-124),避免每次重检引入新的误判。

回收站旧版本快照里还留着一个叫"对手应着"的单行调试脚本(文件时间 2026-09-25 19:17),内容就是打印"修改前 detect_orientation 假设 playing_red=True"与"修改后 playing_red=…",并拿一条具体走法 a5a9 的中文记谱做对照——那个晚上我在干嘛,一目了然。

同一天还有个至今没想明白的插曲:17:27(733f541)加了 551 行的"8 键设置窗口"和 766 行测试;20:04(012d14f)又把它们全部删掉,-1,317 行来去如风。为什么建又删?commit 正文一个字没提。档案没记,我也不编——这算本项目最莫名其妙的一次操作。

## 六、密钥入库:git 历史没有后悔药

2026-08-18(0df1991,+1,500 行)我给项目加了 AI 中文解说:explainer.py 调 DeepSeek 接口,设计原则是"不阻塞主链路"——没配 key 或调用失败就自动降级为"不解释",prompt 里还硬约束大模型"绝对不许改写这步、不许另给建议、不许质疑引擎结论"。同一波还做了全局急停键(hotkey.py:反引号键直读物理键盘状态,因为自动模式下脚本抢走焦点,终端读不到 Q/Esc)和无限对战。

explainer.py 的密钥读取优先级,当时就设计成了显式传参 > 环境变量 > 配置文件——方向是对的,可惜"配置文件"这条路本身就不该放密钥。为了图方便,解说功能的 API key 直接写在了配置代码和配置文件里,然后这两个文件先后进了 git。两个多月后(2026-10-21, 2376729)补 README,我把这事原原本本写进了安全提示:明文 DeepSeek API key 出现于 ai_config.py 与 ai_settings.json 两处,且都已提交进 git 历史。

善后分了两步:8ca39eb(10-21)取消跟踪 ai_settings.json——注意只是"不再跟踪",历史里还在;162788e(2026-10-23)把代码里的密钥换成环境变量:

```python
API_KEY = os.environ.get("DEEPSEEK_API_KEY", "")
```

(ai_config.py,162788e)

但必须说清楚:这两步只保证了"以后的版本"干净。旧密钥仍然躺在 git 历史里,谁克隆仓库翻历史都拿得到;README 里写的建议是吊销旧密钥、重新生成,而要彻底清除历史,得改写全部提交或者干脆重建仓库——远端已经推上去了,这事到今天还没做完。回收站的旧版本快照里,配置文件也还能检出密钥形字符串。教训一句话:密钥永远走环境变量;git 历史是永久的,没有后悔药。

## 七、弯路复盘

1. **二进制大文件进 git,本项目最贵的一课**。8-12 一天之内:4a3ca2f 把约 49,000 行 Pikafish C++ 源码树整个提交进去(125 个文件,+49,351 行);不到两小时后 b569613 又提交了 55MB 的引擎压缩包和 53MB 的 NNUE 权重;16:32 的 9b3806f 删掉 144 个文件(-51,007 行)算是收拾残局。但删除只影响当前版本:53MB 的 NNUE 至今留在 git 历史里。现行 README 白纸黑字把它记为反例:"二进制大文件请走 Releases,不要进 git 历史。"
2. **同日建删的 1,317 行**。见第五节,动机失传。
3. **commit 信息没有信息量**。6bdb282 的全文是"2026,8,14";453c622 的全文是"修了些bug"——修了哪些?没有正文,数据缺失,连我自己都还原不了了。把 commit 信息写清楚,是写给三个月后那个失忆的自己。
4. **训练数据说删就删**。回收站记录显示 08-05~06 有 320 张 CNN 训练图被删除,原因没记录;样本采集脚本 collect_batch.py 从未入库(代码里还有两处引用它),训练流程至今不完全可复现。
5. **AI 编程助手的 checkpoint 差点混进历史**。回收站的 .git 对象里躺着一个 Cline 自动生成的 checkpoint 合并提交 85dbe9c,创建于 08-12 16:27,两分钟后被我 reset 丢弃,没上远端。用 AI 写代码没问题,自动提交不看内容就 merge 这件事,幸好当场发现了。
6. **仓库名拼写**。08-13 上午先建了个 Utimate-Chinese-Chees-Cheat-Tool(两处拼写错误),同日删掉,换名 ultimate-chinese-cheat 重新开张。仓库名要不要这么直白另说,拼写总该查下字典。
